Implemented

Four views of the graph storage schema. Repeated table names refer to the same table.

PK = primary key · FK = foreign key · 1 = one · 0..* = zero or more. Multiple PK fields form a composite key. Key fields shown; implementation columns are omitted.

2. Concepts, claims, and source passages

Claims map to concepts; concepts map to subject areas. Both mappings are many-to-many. Video topics remain source context, and transcript passages remain evidence. Claim text, examples, and extraction IDs are retained from the selected run.

Embeddings: BGE base v1.5 encodes each concept’s name and description, and each source passage’s text. Store the 768-value normalized vector as a PostgreSQL REAL[], with the model ID and pinned revision. Code compares vectors using cosine similarity. Source-passage vectors are shared across systems; concept vectors belong to their graph build. Claims keep their concept and evidence links.

Build boundaries and source tracking

Graph-owned child tables include build_id; graph_build itself uses id, and evidence_span is shared across builds. Composite foreign keys keep claim assignments, memberships, relationships, and merge decisions inside one build. The diagrams omit repeated build_id fields on join tables for space.

graph_claim retains extraction-file and position IDs plus original topic text and examples in JSONB. Its (build_id, video_id) references graph_input. evidence_span stores exact source substrings, offsets, the original chunk time range, and BGE vectors. A timestamp identifies the original source chunk, not a more precise inferred sentence time.

Merge decisions retain both concept records and aliases; claims and evidence are never rewritten. Raw model responses, prompts, timings and issues are saved under data/graphs. Removing a video invalidates and removes any graph built from it.

Models and saved files

Local: the selected DeepSeek model handles all four model stages. API: Luna handles extraction and formatting; Terra handles consolidation and review.

Each run saves its raw responses, pass JSON and guide in its own folder. PostgreSQL tracks videos and run status; files retain timings, settings and API usage/cost. Source passages remain linked by ID. Local inference runs on this computer; the API route sends prompts to OpenAI.

3. Build a graph for each system

Implemented

The model does not re-extract the transcript or assign every claim from scratch. Code seeds concepts from extracted topics, retains the original claims and evidence, and applies model decisions to fixed IDs. BGE suggests candidates; the model decides meaning. Consolidation, subject-area assignment, and relationship generation are separate stages with batches of up to 20 items.

Each system has its own graph built from its own guide runs. DeepSeek uses the selected local model with seed 42. OpenAI uses Terra for consolidation and subject areas, then Luna for relationships. Graph quality depends on both extraction and graph-building output.

4. Index transcript passages

Implemented

Passage vectors are stored once and shared across systems. Concept vectors belong to each graph build. Both use the same BGE model. Retrieval loads PostgreSQL REAL[] vectors and ranks them with NumPy cosine similarity; it does not use full-text search or a separate vector database.

5. Ask Study Desk — four answer modes

Implemented

One question, selected model, and answer mode enter answers.py. Retrieval is code plus BGE; one answer-generation call follows.

All retrieval modes use up to six passages total. Graph retrieval ranks relationships and linked passages, removes duplicate evidence, and fills spare slots from its original candidates. Graph-only starts from concepts rather than a full transcript search. RAG + graph uses the selected system’s graph. Index fingerprints are checked against saved transcript selections.

Retrieved answers attach source IDs to response blocks. The UI renders Markdown, math, and source previews. Graph relationships are retrieval hints; citations refer to transcript evidence. Raw model output is preserved.

6. Evaluation and comparison

Implemented

Local attempts use seed 42; API answers are unseeded. Answer keys are not supplied to models. The runner resumes saved jobs, checks frozen Python hashes, and publishes comparison metadata after progress updates. The comparison tab only reads saved results; it makes no generation calls. Q&A results and experiment manifests are files, not PostgreSQL tables.
